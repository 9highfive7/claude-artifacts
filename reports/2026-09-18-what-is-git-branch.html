概要

3行でいうと
  • Gitのブランチは、ファイルのコピーではなく「特定のコミットを指す軽量なポインタ（矢印）」にすぎない。
  • ブランチを使うことで、本番用のコードに影響を与えずに、機能追加やバグ修正を独立した作業として進められる。
  • 作業が終わったら merge や rebase で元のブランチに取り込むが、両者は履歴の残り方が異なるため使い分けが必要。

「ブランチ」はGitを使ううえで避けて通れない概念ですが、最初は「コピー」や「並行世界」のようなイメージで誤解しやすいものです。 このレポートでは、ブランチの正体（コミットへのポインタ）から、基本コマンド、マージとrebaseの違い、代表的なブランチ戦略、よくあるつまずきポイントまでを整理します。

基本用語

用語意味
commit変更内容のスナップショットを記録した履歴の1単位。前のコミットへの参照（親）を持つ。
ブランチあるコミットを指す軽量なポインタ。コミットするたびに自動的に最新コミットへ移動する。
HEAD「今どのブランチ（またはコミット）にいるか」を示す特殊なポインタ。通常は現在のブランチを指している。
main / masterリポジトリ作成時に自動的にできる既定のブランチ名。近年は main が主流。
fast-forwardマージ先のブランチが、マージ元の直系の祖先である場合に、新しいコミットを作らずポインタを単純に前へ進めるマージ方式。
マージコミット2つの履歴を統合したときにできる、親を2つ持つ特別なコミット。
detached HEADHEADがブランチではなく、特定のコミットを直接指してしまっている状態。
コンフリクト（競合）同じ箇所を異なる内容に変更した2つの履歴をGitが自動的に統合できず、手動での解決が必要になる状態。

仕組み・全体像

3-1. ブランチの正体は「ポインタ」

多くの入門者は「ブランチを作る＝ファイル一式をコピーする」とイメージしがちですが、実際は違います。 Gitのブランチとは、あるコミットのSHA-1ハッシュ値を指し示す、40バイト程度の小さなファイル（参照）にすぎません。

そのため、ブランチの作成はほぼ一瞬で終わり、ディスク容量もほとんど消費しません。

コミットを1つ行うと、今いるブランチのポインタが自動的にその新しいコミットへ移動します。 複数のブランチが同じコミットを指すこともできますし、開発が進むにつれてそれぞれ別のコミット列を指すようになります。

3-2. HEADは「今いる場所」を示す

HEADは「現在作業しているブランチ」を指す特殊なポインタです。 git switchやgit checkoutでブランチを切り替えると、HEADが指す先が変わります。 ここで新しくコミットすると、HEADが指しているブランチのポインタだけが前進し、他のブランチには影響しません。

なお、コミットハッシュを直接指定して checkout すると、HEADがブランチではなくコミットを直接指す「detached HEAD（分離HEAD）」状態になります。 この状態のまま新しいコミットを作ると、あとでどのブランチからも参照されない「迷子コミット」になりやすいため注意が必要です（詳しくは5章）。

3-3. 基本コマンド

# ブランチの一覧を見る
git branch

# 新しいブランチを作る（切り替えはしない）
git branch feature/login

# ブランチを作って同時に切り替える
git switch -c feature/login
# 従来の書き方（今も使える）
git checkout -b feature/login

# ブランチを切り替える
git switch main
git checkout main

# ブランチをmainに統合する
git switch main
git merge feature/login

# 不要になったブランチを削除する
git branch -d feature/login

Git 2.23（2019年公開）以降は、ブランチ切り替え専用の git switch と、ファイルを元に戻す専用の git restore が追加されました。

従来の git checkout はブランチ切り替え・コミットのチェックアウト・ファイルの復元まで何でもこなす万能コマンドで便利な反面、 意図しないdetached HEADを招きやすいという弱点がありました。初心者にはより安全な git switch / git restore の利用が推奨されています。

3-4. マージとrebaseの違い

枝分かれしたブランチを1本に統合する方法には、主に merge と rebase の2種類があります。

git mergegit rebase
履歴 そのまま残す（非破壊的） コミットを別の土台の上に「再適用」し、履歴を書き換える
結果の形 分岐・合流を表すマージコミットができ、履歴は枝分かれした形（非直線的）になる コミットが一直線に並ぶ（直線的な履歴になる）
向いている場面 他の人と共有しているブランチを統合するとき まだ共有していない自分の作業ブランチの履歴を整理したいとき
注意

すでにリモートで他の人と共有しているブランチに対して rebase を行うと、コミット履歴（ハッシュ値）が書き換わってしまい、他の人のローカル履歴と食い違いが生じます。共有ブランチのrebaseは避けるのが原則です。

具体例・使いどころ

4-1. 典型的な作業の流れ

  1. mainブランチから新しいブランチ（例：feature/add-login）を作る。
  2. そのブランチ上でコミットを積み重ねながら機能を実装する。
  3. 作業中にmain側で他の変更が進んでいても、ブランチが分かれているので互いに干渉しない。
  4. 実装が完了したらプルリクエスト（Pull Request）を作成し、レビューを経てからmainへマージする。
  5. 不要になった作業ブランチは削除する。

4-2. 代表的なブランチ戦略

戦略特徴向いているケース
Git Flow main・develop・feature・release・hotfixなど複数の長期ブランチを役割ごとに分ける、やや重厚な運用 バージョンを区切ってリリースするアプリ（モバイルアプリ、SDK、パッケージ製品など）
GitHub Flow 長期ブランチはmainのみ。mainから短命の作業ブランチを切り、Pull Request経由でマージする 継続的にデプロイする小〜中規模チームのWebサービス開発
トランクベース開発 ブランチをほぼ作らず、1日に何度もmain（トランク）へ直接、または非常に短命のブランチ経由で統合する CI/CDとテストが十分に整備された、経験豊富なチーム

注意点・よくある誤解

「ブランチ＝ファイルのコピー」という誤解

実際にはコピーではなく、コミットを指すポインタが増えるだけです。ブランチ作成が一瞬で終わるのはこのためです。

detached HEAD状態に気づかずコミットしてしまう

コミットハッシュやタグを直接checkoutすると、ブランチではなくコミットに直接HEADが付いた状態（detached HEAD）になります。

この状態で作業してコミットすると、後で別のブランチに切り替えた瞬間にそのコミット群がどのブランチからも参照されなくなり、 いずれガベージコレクションの対象になって消えてしまう可能性があります。作業を始める前に、自分がブランチ上にいるか（git statusやgit branchで確認）をチェックする習慣が重要です。

共有ブランチをrebaseしてしまう

他の人と共有しているブランチの履歴をrebaseで書き換えると、リモートとローカルで履歴が食い違い、混乱やコンフリクトの温床になります。rebaseは「まだ自分だけが使っている、共有前のブランチ」に限定するのが安全です。

長生きしすぎるブランチはコンフリクトの元

作業ブランチを長期間mainから更新せずに放置すると、双方の変更が積み重なり、マージ時に大きなコンフリクトが発生しやすくなります。

こまめに（少なくとも1日1回程度は）最新のmainを取り込む、ブランチの寿命を短く保つといった運用が、コンフリクトの予防に有効です。

コンフリクトは「異常」ではない

複数人が同じ箇所を変更すれば当然起こり得るものです。エディタ上に表示される <<<<<<< / ======= / >>>>>>> の記号で挟まれた部分を確認し、どちらの内容を残すか（あるいは両方を組み合わせるか）を決めて保存し直せば解決できます。

確認問題

Q1. Gitのブランチの実体として最も正確なものはどれか。

ブランチとは、あるコミットを指す軽量なポインタ（参照）である。ファイル一式のコピーではない。コミットするたびに、現在のブランチのポインタが自動的に最新のコミットへ移動する。

Q2. HEADとは何を指しているか。

現在作業しているブランチ（または特定のコミット）を示す特殊なポインタ。通常はブランチを指しているが、コミットを直接checkoutすると「detached HEAD」状態になり、ブランチではなくコミットそのものを直接指す。

Q3. git mergeとgit rebaseの違いを説明せよ。

mergeは元の履歴をそのまま残し、2つの履歴をつなぐマージコミットを新しく作る（非破壊的、履歴は枝分かれした形になる）。 rebaseはコミットを別の土台の上に再適用することで履歴を直線的に書き換える（破壊的、共有済みブランチには使わない方がよい）。

Q4. fast-forwardマージが起こるのはどのような条件のときか。

マージ先のブランチが指すコミットが、マージ元のブランチの直系の祖先になっている（つまりマージ先で新しいコミットが積まれていない）場合。この場合Gitは新しいマージコミットを作らず、ポインタを単純に前へ進めるだけで済ませる。

Q5. 作業ブランチを長期間放置するとどのような問題が起きやすいか。またその対策は？

main側と作業ブランチ側の双方で変更が積み重なり、マージ時に大きなコンフリクトが発生しやすくなる。対策として、ブランチの寿命を短く保つこと、こまめに（例えば1日1回程度）最新のmainを作業ブランチに取り込むことが有効。
