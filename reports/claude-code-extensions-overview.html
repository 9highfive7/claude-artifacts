Claude Code の拡張の全体像：どの仕組みをいつ使うか

  • 作成日 2026-10-03
  • 確認日 2026-10-03（公式ドキュメント code.claude.com を参照）
  • 分野 AI／開発

概要

3行でいうと
  1. Claude Codeの拡張は、モデルが読む指示（CLAUDE.md・Skill）、本体が実行する仕組み（Hooks・settings.json）、別の担い手を足す仕組み（サブエージェント・MCP）、それらを束ねる箱（プラグイン）に分けて考えると整理しやすい。
  2. 「必ず動かしたい」ことはCLAUDE.mdやSkillに書かず、Hooksとsettings.jsonのpermissionsに置く。前者はモデルが解釈する文脈で、後者は本体が強制する。
  3. ハーネスは拡張の部品ではなく、モデルを包む層の全体を指す呼び名である。Modsはプラグインの一種として公式に位置づけられている。

この文書の確認日は2026-10-03である。Claude Codeは更新が速いため、機能名や挙動は公式ドキュメントで再確認してほしい。公式ページで確かめられなかった項目は「未確認」と書き、推測では埋めていない。

扱うのはCLAUDE.md、Skill、Hooks、サブエージェント、MCP、settings.json、プラグイン、ハーネス、Modsの9項目である。比較は「いつ読み込まれるか」「誰が実行するか」「確実に動くか（決定的か）」「コンテキストを消費するか」の4観点で行う。説明の中で、このリポジトリ（claude-artifacts）の.claude/配下を実例として引用する。

基本用語

用語意味
コンテキストモデルが1回の応答で見る情報の全体。会話履歴、読んだファイル、CLAUDE.md、読み込み済みのSkillなどが入る。大きくなるほど余裕が減る
決定的同じ条件なら毎回同じ結果になること。ここでは「発火や強制が保証されること」の意味で使う。モデルの解釈を挟むものは決定的ではない
CLAUDE.mdプロジェクトの規約や「いつもこうする」を書くmarkdown。毎セッションの開始時にコンテキストへ読み込まれる
SkillSKILL.mdに書いた手順書や参考資料。説明文だけ常に見え、本文は使うときに読み込まれる。/名前で人が呼ぶことも、Claudeが自分で呼ぶこともできる
Hookライフサイクルのイベント（ツール実行の前後、セッション開始など）でClaude Code本体が動かす処理。シェルコマンド、HTTP、MCPツール、プロンプト、サブエージェントの5種類がある
サブエージェント独立したコンテキストで動く作業役。結果の要約だけがメインの会話に戻る
MCP外部サービスやツールをつなぐオープンな規格。Claude CodeがMCPクライアントになり、MCPサーバーのツールをClaudeが呼ぶ
settings.json権限（permissions）、hooks、モデルなどを書く設定ファイル。管理者・コマンドライン・ローカル・プロジェクト・ユーザーの5階層がある
プラグインSkill、エージェント、Hooks、MCPサーバーなどを1つにまとめてインストールできる単位
ハーネスモデルにツールを与え、見える情報（コンテキスト）を管理する周辺層の呼び名。公式ドキュメントの「How Claude Code works」に登場する
ModsJavaScriptやTypeScriptの関数でイベントを処理し、画面の描画なども変えられるプラグイン

MCPの仕組みそのものは、既存ノートMCP（Model Context Protocol）とは何かにまとまっている。ここではMCPを拡張の一部として位置づけるにとどめる。

仕組み・全体像

拡張の層と読み込みの流れ

Claude Codeの中心には、モデルが考えてツールで作業する「エージェントループ」（文脈を集める、行動する、結果を確かめる）がある。公式ドキュメントは、拡張をこのループの別々の場所に差し込む部品として説明している。

  • 常に見える文脈を足す：CLAUDE.md
  • 必要なときに知識や手順を足す：Skill
  • 外部のツールとデータをつなぐ：MCP
  • 別の作業空間で動かす：サブエージェント
  • イベントで本体がスクリプトなどを動かす：Hooks
  • これらを配布用にまとめる：プラグイン

settings.jsonはこの部品群のどれとも少し性質が違う。モデルへの指示ではなく、本体の挙動（許可・拒否、フックの登録など）を決める設定である。公式の権限ページには「権限ルールはClaude Codeが強制するもので、モデルが強制するものではない。プロンプトやCLAUDE.mdの指示はClaudeが何を試みるかを左右するが、Claude Codeが何を許可するかは変えない」という趣旨の注記がある。

4観点の比較表

次の表は、公式ドキュメント（Extend Claude Code、メモリ、Hooks、権限、プラグイン、Modsの各ページ）から確認できた内容をまとめたものである。ページに書かれていない欄は「未確認」としている。

拡張9項目の比較（確認日2026-10-03）
項目いつ読み込まれるか誰が実行するか確実に動くか（決定的か）コンテキストを消費するか

Skill 名前と説明はセッション開始時。本文は/名前で呼ばれたとき、またはClaudeが必要と判断したとき Claudeが本文を読んで従う。起動は人でもClaudeでもよい 決定的ではない。「Claudeが指示を解釈し、結果は変わりうる」と公式が説明 説明文だけ常時。本文は使用時。disable-model-invocation: trueなら呼ぶまで説明も入らない
Hooks 設定ファイルに登録しておき、対応するイベントが起きたとき Claude Code本体が、シェルコマンド・HTTP・MCPツール・プロンプト・サブエージェントのいずれかを動かす 発火は保証される。command・http・mcp_tool型は固定ロジックで決定的。prompt・agent型はLLMを使う 原則ゼロ。フックが出力を返したときだけ、その分が会話に入る

MCP セッション開始時にツール名とサーバーの説明。詳しいスキーマは必要になってから（ツール検索が既定で有効） MCPサーバーのプロセスがツールを実行する。Claudeは呼ぶ側で、コードを直接動かさない 呼ぶかどうかはモデルの判断で決定的ではない。呼ばれた後の中身はサーバー側のコードで動く 使うまでは少ない。使うと結果がコンテキストに入る
settings.json 起動時に読む。5階層（管理者、コマンドライン、ローカル、プロジェクト、ユーザー）で上位が優先 Claude Code本体（モデルではない） 権限ルールは本体が強制する。判定順はdeny、ask、allow 設定ファイル全体がコンテキストに入るかは未確認。ツール名だけのdenyルールは、そのツールをコンテキストから消す
プラグイン インストールして有効にした後、セッション起動時（途中なら/reload-plugins） 中身による。SkillはClaude、Hooksは本体、MCPサーバーはそのプロセス 中身による。プラグイン自体に決定性はない 有効な間は、Claudeが自分で呼べるSkill・エージェントの名前と説明が毎ターン入る。本文は使用時
ハーネス 該当しない（拡張の部品ではなく、全体の呼び名） 該当しない 該当しない 該当しない
Mods プラグインとして有効になったとき（途中なら/reload-plugins）。Claude Code v2.1.287以降で既定で有効 Claude Codeのプロセス内で、プラグインに入ったJavaScript・TypeScriptの関数が動く イベントが起きたら、本体が先にその関数を呼ぶ。関数の中身は書いたコード次第。LLMを介するかどうかは書き方による 未確認。公式の概要ページに一律の記載はない。プロンプトを書き換える処理は可能と書かれている
補足

「決定的」の意味は欄によって少し違う。Hooksでは「イベントが起きたら必ず動く」という発火の保証を指す。settings.jsonのpermissionsでは「本体が必ず強制する」を指す。CLAUDE.mdとSkillは、どちらもモデルが読んで従うかどうかを決めるため、この意味では保証がない。

ハーネスとModsの位置づけ

定義があいまいな2項目は、公式ドキュメントでの扱いを先に確認した。

用語公式での位置づけ確認できたこと
ハーネス 全体の呼び名。拡張の部品ではない 「How Claude Code works」に、Claude Codeはツールを提供しモデルの見る情報を管理する周辺層であり、この層をagentic harnessと呼ぶ、という趣旨の記述がある。専用の解説ページはllms.txtの目次に見当たらない。Anthropic以外の解説記事でも同様の意味で使われているが、一次情報ではないので定義には採用していない
Mods プラグインの一種（拡張の部品） 「modは、Claude Codeの見た目と振る舞いを変えるプラグイン」と定義されている。イベントハンドラをJavaScript・TypeScriptで書き、Claude Code自身のプロセス内で動く。画面のペイン描画、ツール呼び出しへの介入、独自の/コマンドの追加ができる。プレビュー等の表記は取得した本文に見当たらない（未確認）

ModsとHooksは名前が紛らわしい。Modsのページは、Claude Codeが両方をhooksと呼ぶと断ったうえで、設定ファイルに書くものを「settings hook」、modの関数を「hook」と区別している。settings hookは外部のスクリプトを動かし、modは本体の内側で動く。そのためmodには画面を描くことができるが、settings hookにはできない。

Modsはユーザーの権限で動くコードで、サンドボックスの外で子プロセスを起動できる。公式は信頼できる作者と配布元のものだけを入れるよう警告している。この種のリスクはAIセキュリティ入門 — 守る側のための教科書が扱うエージェントやサプライチェーンの話と同じ筋にある。

やりたいこと別の選び方

公式の「Extend Claude Code」には、困りごとのきっかけから追加する拡張を選ぶ表がある。それを元に、判断の順序を次の表にした。上から順に当てはめる。

やりたいこと使うもの理由
毎回知っておいてほしい規約・コマンド・構成を伝えるCLAUDE.md毎セッション自動で読まれる。公式は「同じ間違いを2回したら足す」を目安にしている
これだけは必ず守らせたい禁止事項（例: force push禁止）settings.jsonのpermissions（deny）、またはPreToolUseのHook本体が強制する。CLAUDE.mdへの一文は「お願い」にとどまる
編集のたびに整形する、実行のたびに記録する、のように毎回必ず動かすHooksイベントで確実に発火し、判断が要らない処理に向く
同じ手順書を毎回貼っている、/名前で始めたいSkill必要なときだけ本文が入る。手順の適用はClaudeが考える
大量のファイルを読む調べ物で、結果の要約だけがほしいサブエージェント作業がメインのコンテキストを汚さない
外部サービスのデータや操作が必要（DB、Slack、ブラウザなど）MCP接続と認証をサーバー側が担う。使い方の知識はSkillと組み合わせる
数十から数百のエージェントを動かし、結果を相互検証したいDynamic workflows進行をスクリプトが握る。詳細は下の「ほかにある拡張」
別のリポジトリや他の人にも同じ設定を配りたいプラグインSkill・エージェント・Hooks・MCPを1単位で配布できる
画面に自作のパネルを出す、ツール呼び出しやプロンプトを書き換えるMods本体の内側で動くので、外側の仕組みでは届かない領域を扱える
応答の口調・長さ・形式を変えたいOutput style公式の機能一覧にある。CLAUDE.mdは「何を知るか」、Output styleは「どう答えるか」

図の元になる考え方は2つの問いに絞れる。1つ目は「モデルが守らなくても必ず起きなければならないか」で、はいならHooksかpermissionsを選ぶ。2つ目は「常に必要か、ときどき必要か」で、常にならCLAUDE.md、ときどきならSkillを選ぶ。そのうえで、外部につなぐならMCP、作業を分離するならサブエージェント、配るならプラグインを足す。

確実性が高いものほど融通が利かず、融通が利くものほど確実性が下がる。確実さが必要な処理はHooksとpermissionsに、判断が必要な処理はSkillとサブエージェントに任せる、という分担になる。この「手順をコードで固定するか、モデルに任せるか」の軸は、既存ノートAIエージェントとワークフローの違いの整理とほぼ同じ構図である。

具体例・使いどころ

リポジトリの .claude/構成

このリポジトリは、学習レポートをHTMLにしてGitHub Pagesで公開するためのものである。次の対応表のとおり、拡張の多くを実際に使っている。なお.mcp.json、.claude/rules/、.claude/workflows/、.claude/commands/、settings.local.jsonは見つからなかった（2026-10-03時点）。

拡張このリポジトリでの実体使い方
CLAUDE.mdリポジトリ直下のCLAUDE.md構成とルールを書いている
settings.json.claude/settings.jsonpermissionsとhooksを定義している
Hooks.claude/hooks/log-usage.jsgit pushの直後にコストを記録する
サブエージェント.claude/agents/researcher.md、designer.md調査・初稿と、デザイン仕上げを分担する
Skill.claude/skills/のreport、readable-html-layout、yomiyasu作業手順と、レイアウトや文章の基準を持つ
MCPなし（.mcp.jsonが存在しない）このリポジトリでは使っていない
プラグイン・Modssettings.jsonに有効化の記載なし使っていない

実例：CLAUDE.md

CLAUDE.mdには「出力・報告はすべて日本語」「ファイル名はreports/<英小文字とハイフンのスラッグ>.html」「git push --forceは絶対に使わない」などが書かれている。これらは毎セッションの文脈として読まれる。

注目点はforce pushの扱いである。CLAUDE.mdの一文だけでは「お願い」だが、このリポジトリはsettings.jsonのdenyにも同じ禁止を重ねている。確実に止めたい項目を二重にしている例である。

実例：settings.jsonのpermissions

.claude/settings.jsonのpermissionsは次のとおりである（抜粋）。

"allow": [ "WebSearch", "WebFetch", "Read",
           "Edit(reports/**)", "Edit(index.html)",
           "Bash(git status)", "Bash(git add:*)", "Bash(git commit:*)",
           "Bash(git push origin main)", "Bash(git log:*)", ... ],
"deny":  [ "Bash(git push --force:*)", "Bash(git push -f:*)" ]

編集はreports/配下とindex.htmlに限り、pushはorigin mainだけを許している。公式の判定順はdeny、ask、allowの順で、最初に当たったものが結果になる。denyに当たるforce pushは、allowに似たルールがあっても止まる。この強制は本体が行うので、モデルの気分に左右されない。

実例：Hooksとlog-usage.js

同じsettings.jsonのhooksでは、PostToolUseに"matcher": "Bash|PowerShell"を指定し、node ".../.claude/hooks/log-usage.js"をtimeout: 40で動かしている。

matcherはBashツールの実行ごとに当たるため、フックはgit以外のコマンドでも毎回起動する。絞り込みはスクリプト側の正規表現（/\bgit\s+push\b/）が担っている。pushが失敗していたら記録せず、成功していれば会話ログからトークン数を集計し、reports/usage-log.csvに追記して自分でcommitとpushを行う。末尾のprocess.exit(0)により、失敗してもメインの作業を止めない。

PostToolUseはツールがすでに動いた後なので、止める用途には使えない。このリポジトリのフックは「記録する」だけで、判断をモデルに任せる必要がない。Hooksが得意とする処理にあたる。フックの中のpushはClaudeのBashツールを通らず、スクリプトが直接gitを呼んでいるので、フック自身をもう一度起動する構造にはなっていない。

実例：サブエージェントの定義

.claude/agents/の2つは、frontmatterの書き方が違う。

項目researcher.mddesigner.md
description学習テーマをWebで調べ、reports/にHTMLの初稿を作る。/reportスキルの調査工程で使うresearcherが作ったHTMLを「書き込みノート」デザインで仕上げる。/reportスキルの仕上げ工程で使う
toolsWebSearch, WebFetch, Read, Write, Glob記載なし（省略時の既定の扱いは今回確認できず、未確認）
modelclaude-sonnet-5-5claude-opus-5-5

researcherはtoolsを明示してBashやEditを持たせず、調査と書き出しに必要な道具だけを渡している。モデルはフルIDで固定している。reportスキルには「別名のsonnetを渡すと版が変わることがあるので、定義のIDをそのまま使う」という趣旨の注意がある。公式ドキュメントでは、modelにsonnetなどの別名とフルIDの両方を書けるとされている。

この2つは、スキルから順番に呼ばれる分業役である。委任するかどうかはdescriptionを読んだClaudeが決める仕組みなので、descriptionには「どの工程で使うか」まで書いてある。

実例：Skillの定義

.claude/skills/には3つのSkillがあり、それぞれSKILL.mdのfrontmatterにnameとdescriptionを持つ。

Skill役割frontmatterの特徴
reportテーマを受け取り、調査、HTML作成、デザイン、index更新、push、報告まで一括で行うargument-hint: <学びたいテーマ>を持つ。/reportで呼べる。「〇〇をレポートにして」と頼んでも使われる
readable-html-layout読みやすいHTMLレイアウトの数値基準と判断の目安descriptionが長く、使う場面を細かく列挙している。Claudeが自動で選ぶための手がかり
yomiyasuAIっぽい日本語を自然な文章に直すlicense: MITとargument-hintを持つ。plugin形式のファイル（.claude-plugin/）も同梱されているが、このリポジトリでは.claude/skills/に置いている

reportのSKILL.mdは、調査をresearcher、仕上げをdesignerに渡し、間にyomiyasuを挟む手順書である。つまりSkillが全体の段取りを持ち、サブエージェントが作業を担い、フックが最後に記録する。拡張同士を組み合わせた典型例で、公式の「Skill + Subagent」「Hook +外部処理」の型に近い。

reportは.claude/skills/report/extract_text.pyという補助スクリプトも持つ。Skillはフォルダ単位で、SKILL.mdのほかに実行用のファイルを置ける。

実例：拡張の連携

ここまでの流れを1本にすると、次のようになる。

  1. 人が/report テーマを実行する。Skill（report）の本文が読み込まれる。
  2. Skillの手順に従い、Claudeがresearcher、次にdesignerを呼ぶ（サブエージェント）。
  3. 各工程で、settings.jsonのpermissionsが許可・拒否を判定する。
  4. 最後にgit push origin mainが成功すると、PostToolUseのフックが動き、コストを記録する。

このうち1と2はモデルが解釈する部分で、3と4は本体が確実に動かす部分である。確実性の高い処理が後ろに寄っているので、途中のモデルの揺れが記録や権限を壊しにくい。

ほかにある拡張

公式ドキュメントの目次（2026-10-03時点）には、主題の9項目以外にも次の機能がある。名前の紹介にとどめる。

  • Dynamic workflows：Claudeが書いたJavaScriptのスクリプトが多数のサブエージェントを動かし、最終結果だけを返す。次に何を動かすかを決めるのがモデルではなくスクリプトである点が、サブエージェント単体との違い。詳しくはDynamic Workflows 実践ガイド — Claude Codeを参照。
  • Routines：保存したプロンプト・リポジトリ・コネクタを、スケジュール、API呼び出し、GitHubイベントでAnthropicのクラウド上で自動実行する。公式ページには「research preview」と明記されており、挙動や上限が変わる可能性がある。
  • Output styles：役割・口調・応答形式をセッション単位で切り替える。
  • Cross-session messaging、Agent teams、Artifacts：セッション間の連絡、複数セッションの協調、出力の共有ページ化。詳細は今回未確認。

注意点・よくある誤解

よくある誤解1

「CLAUDE.mdに書けば必ず守られる」は誤り。公式はCLAUDE.mdを文脈として扱い、強制される設定ではないと明記している。書き方が具体的で短いほど守られやすいが、保証にはならない。必ず守らせたいことはHooksかpermissionsに置く。

よくある誤解2

「Skillは呼ばれたら確実に同じ手順で動く」も誤り。SkillはClaudeが読んで従う指示で、結果は変わりうる。また、会話が長くなって圧縮されると内容が削られることがあり、公式は「必ず守らせたいルールはHookにする」と案内している。

よくある誤解3

「Hooksは何でも止められる」とは限らない。止められるかはイベントで決まる。PreToolUseは実行前に止められるが、このリポジトリで使っているPostToolUseはツールがすでに動いた後なので止められない。用途が違う。

よくある誤解4

「ハーネスはClaude Codeの機能の1つ」ではない。公式ドキュメントの使い方では、Claude Codeが提供するツールとコンテキスト管理の層全体を指す呼び名である。SkillやHooksと並べて「どれを選ぶか」を考える対象ではない。

よくある誤解5

「ModsはHooksの新しい呼び名」でもない。Modsはプラグインの一種で、本体の内側で動く関数である。設定ファイルに書くHooksは外側で動くスクリプトで、画面は描けない。公式はどちらもhookと呼ぶと断っているため、文書を読むときは「settings hook」か「modのhook」かを確かめる。

補足：入れすぎにも注意

公式は、拡張を足すほどコンテキストを消費し、Skillが正しく選ばれなくなったり、規約を見失ったりしうると述べている。プラグインは有効にしている間、使わないセッションでもSkillやエージェントの名前と説明がコンテキストに入る。最初から全部を入れず、困りごとが出てから1つずつ足す方針が公式でも勧められている。

補足：信頼できるものだけを入れる

プラグイン、Mods、MCPサーバーは、自分の権限で動くコードや、外部の内容を持ち込む入口になる。公式も、信頼できる配布元のものだけを入れ、MCPは接続前にサーバーを確認するよう警告している。プロンプトインジェクションの観点はAIセキュリティ入門 — 守る側のための教科書を参照。プラグインの概念はClaude Cowork でできること — はじめての人のための活用ガイドにも出てくる。

確認問題

Q1. 「このファイルは絶対に編集させない」を実現したい。CLAUDE.mdへの一文と、settings.jsonのdenyルールやPreToolUseのHookでは、何が違うか。

CLAUDE.mdは文脈であり、モデルが従うかどうかは保証されない。denyルールやPreToolUseのHookはClaude Code本体が実行前に判定して止めるので、モデルの判断に関わらず強制される。確実さが必要なら後者を使う。

Q2. SkillとCLAUDE.mdの読み込みタイミングの違いを説明せよ。

CLAUDE.mdはセッション開始時に全文が読み込まれ、毎リクエストに乗る。Skillは名前と説明だけが開始時に入り、本文は呼ばれたとき（人が/名前と打つか、Claudeが必要と判断したとき）に読み込まれる。「毎回必要」ならCLAUDE.md、「ときどき必要」ならSkillが向く。

Q3. このリポジトリのlog-usage.jsがPostToolUseのHookで適しているのはなぜか。

やることが「git pushの成功後にコストを記録する」という固定の処理で、モデルの判断が要らないため。Hooksは対応イベントで確実に発火し、フックの出力を返さない限りコンテキストを消費しない。ツールの実行後に動くPostToolUseなので、止める用途ではなく記録の用途に合っている。

Q4. ハーネスとModsは、9項目の比較表の中でそれぞれどう扱われるか。

ハーネスは拡張の部品ではなく、モデルにツールを与えコンテキストを管理する周辺層（Claude Codeそのもの）の呼び名なので、4観点は該当しない。Modsは公式にプラグインの一種とされ、Claude Codeのプロセス内でJavaScript・TypeScriptの関数としてイベントを処理する。コンテキスト消費については公式の一律の記載が未確認である。

Q5. 大量のファイルを読んで調べ物をさせたいが、メインの会話を汚したくない。どの拡張を選び、何が会話に戻るか。

サブエージェントを選ぶ。独立したコンテキストで作業し、メインの会話には結果の要約だけが戻る。規模がさらに大きくなり、数十以上のエージェントを動かしたいならDynamic workflowsを検討する。
