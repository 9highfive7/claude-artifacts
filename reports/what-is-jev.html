Jev とは何か

「文章を書かないAI」をやさしく解説

2026年9月15日、TypeSafe AI という会社が Jev（ジェブ） という新しいAIを発表しました。ChatGPT のように文章で答えるのではなく、「AかBか」「何点か」「はい/いいえ」といった判断だけを、とても速く・安く返すのが特徴です。この資料では、AIに詳しくない人でも「何が新しいのか」「どう使うのか」「何に注意すべきか」が分かるように説明します。

この資料の読み方 上から順に読めば分かるように書いています。時間がなければ 30秒サマリー だけでもOK。分からない言葉が出てきたら 用語集 を見てください。「＋ もっと詳しく」の欄は、技術的に踏み込みたい人向けなので飛ばして構いません。

30秒サマリー

  1. 何が出た？元OpenAI（ChatGPTを作った会社）の研究者が立ち上げた TypeSafe AI という会社が、Jev という新しいAIを発表。開発資金として4,000万ドル（約60億円規模）を調達しています。
  2. 何が違う？ChatGPT は「文章」で答えますが、Jev は文章を一切書きません。あらかじめ決めた選択肢から選ぶ、点数をつける、はい/いいえで答える——この3種類の「判断」だけを返します。
  3. 何がうれしい？プログラムから使いやすく、ChatGPT系のAIより桁違いに速くて安い（開発元の計測で、同程度の賢さのAIと比べて速度25倍・費用は約1/76）。開発元の主張
  4. 弱点は？「間違えない」わけではありません。返事の形は崩れませんが、中身が間違うことはあります。最上位のAIと比べると賢さは少し劣ります。
  5. 私たちにとっての意味は？「AIを乗り換える」話ではなく、「AIに文章で丸投げしていた仕事のうち、実は“分類・判定”だけで済むものを切り分ける」という考え方の話。これは Jev を使わなくても今日から役立ちます。

1.前提：今のAIは「文章を書く」道具

要点ChatGPT などのAI（LLM）は人間が読む文章を作るのが仕事。だからプログラムから使うと「文章を読み取って形を整える」手間が発生する。

ChatGPT や Claude のようなAIは、まとめて LLM（大規模言語モデル）と呼ばれます。文章で質問すると文章で答えてくれる、とても便利な道具です。

ところが、この「文章で答える」という性質は、人間ではなくプログラムが答えを使いたいときには不便になります。たとえば「この問い合わせは請求の話か、技術の話か、営業の話か」をAIに判定させて、その結果で担当部署を自動で振り分けたいとします。AIは「この問い合わせは請求に関する内容と思われます。ただし…」のような文章で返してくるので、プログラム側で次の作業が必要になります。

  • 文章の中から「請求」という答えを読み取る（解析する）
  • 期待した形（3つのどれか）になっているか確認する
  • 「分かりません」「両方かもしれません」のような想定外の返事に備える

図1　今のAI（LLM）をプログラムから使うときの流れ。AIの答えが「文章」なので、プログラムが使える形に直す工程（赤）が必ず挟まる。

この「文章をプログラム用に直す」工程は、地味ですが手間がかかり、AIの返事が少し変わるだけで壊れることもあります。Jev はここを丸ごとなくそうという発想で作られています。

2.Jev は何が違うのか

要点Jev には「状況」と「型の決まった質問」を渡す。返ってくるのは文章ではなく「選択肢・点数・確率」なので、プログラムがそのまま使える。

例え話：記述式テストとマークシート

ChatGPT は記述式の答案を書く生徒です。内容は豊かですが、採点する側が読んで判断しなければなりません。

Jev はマークシート専門の生徒です。「AかBかCか」「5段階で何点か」「○か×か」にしか答えませんが、答えは機械で即座に読み取れます。しかも各回答に「自信あり／なし」の印まで付けてくれます。

Jev に渡すものは2つだけです。

  1. 状況（state）判断の材料になるデータ。「顧客からの問い合わせ文」でも、注文履歴のようなデータでもOK。
  2. 質問（questions）「型」を決めた質問。答え方が3種類に限定されています（次の表）。何問でもまとめて聞けます。

図2　Jev をプログラムから使うときの流れ。答えは最初から「プログラムが使える形」で返ってくるので、図1の赤い工程が消える。

質問の3つの型

出典：TypeSafe 公式ドキュメント（Primitives）。日常的な例で言い換えています。
型どんな質問？返ってくるもの使う場面の例
Choice
選択		 この選択肢のうちどれ？ 選ばれた選択肢＋各選択肢の確率＋信頼度 問い合わせを「請求／技術／営業」のどれかに振り分ける。書類の種類を判定する。

点数		 どのレベル？ 自分で決めた尺度上の点数（レベルの間の小数も返る）＋確率＋信頼度 顧客の怒り度を3段階で。障害の重大さを5段階で。文章の品質を採点する。
Noul
はい/いいえ		 これは本当？ 「はい」である確率（0〜1） 返金の要求か？　バグ報告か？　個人情報が含まれているか？
いちばん大事な考え方：「AIが答え、プログラムが決める」

Jev の公式ドキュメントが繰り返し言っているのは、大きな判断を小さな質問に分けなさいということです。

  • ×「この経費申請を承認していい？」と丸ごと聞く
  • ○「領収書は読める？」「費目は何？」「申請内容は領収書と一致する？」と分けて聞く
  • そのうえで「食事代が$75超で内容が不一致なら上司承認、それ以外は承認」というルールはプログラム側に書く

こうしておくと、社内ルールが変わったときも AI への質問はそのままで、プログラムのルールを書き換えるだけで済みます。

3.使い方を具体例で見る

要点「サポート問い合わせを1通渡して、3つの質問に同時に答えさせる」だけで、振り分け・優先度付けの材料がそろう。

公式のサンプルをもとに、日本語で流れを追ってみます。お客様からこんな問い合わせが来たとします。

「Stripe（決済サービス）のアカウント連携を3日間試しているのにずっと失敗します。売上が減っていて困っています。至急助けてください。」

この文章を「状況」として渡し、3つの質問を同時に投げます。

質問型選択肢／尺度Jev の答え
どの部署が担当すべき？選択請求／技術／営業技術
お客様はどれくらい怒っている？点数0：冷静／1：不満だが丁寧／2：かなり怒っている1.035（「不満だが丁寧」よりやや上）
急ぎの内容？はい/いいえ—0.999（ほぼ確実に「はい」）

あとはプログラム側で「技術チームのキューに入れる」「急ぎなので優先度を上げる」「怒り度が高ければベテランに回す」といった処理を書くだけです。返信文を書くのは Jev の仕事ではないので、返信が必要なら ChatGPT のような文章を書くAIに別途頼みます。役割分担です。

もっと詳しく：実際のプログラム（公式クイックスタートより）

上の表を Python で書くと次のようになります。Choice・Score・Noul が3つの型に対応しています。

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()

ticket = "Hi, I've been trying to connect my Stripe account for 3 days and it keeps failing. I'm losing sales. Please help ASAP."

response = client.system_one(
    state=ticket,
    questions={
        "department": Choice(
            instructions="Which team should handle this",
            criteria={
                "billing": "Payment or subscription issues",
                "technical": "Bugs or integration problems",
                "sales": "Pricing or account questions",
            },
        ),
        "frustration": Score(
            instructions="How frustrated the customer appears",
            criteria=[
                "Calm, just stating facts",
                "Frustrated but civil",
                "Very angry, strong language",
            ],
        ),
        "is_urgent": Noul(
            instructions="The message conveys urgency or time-sensitivity",
        ),
    },
)

print(response.answers["department"].choice)  # "technical"
print(response.answers["frustration"].score)  # 1.035
print(response.answers["is_urgent"].noul)     # 0.999

質問はいくつ足しても1回の呼び出しにまとめられます。公式資料では、13問を1回にまとめると、13回に分けて聞くより 11.5倍安く、9.6倍速く、答えは変わらなかったと報告されています。「使うか分からない質問も先に全部聞いて、要らない答えはプログラム側で捨てる」使い方が推奨されています。

4.なぜ速くて安いのか

要点文章を書くAIは「1文字ずつ順番に」作るので時間がかかる。Jev は答えの形が決まっているので「全部いっぺんに」出せる。

ChatGPT のようなAIは、実は文章を1単語（正確には1トークン）ずつ順番に作っています。前の単語を見て次の単語を決める、を何百回も繰り返すので、長い答えほど時間と計算コストがかかります。

Jev は「選択肢のどれか」「何点か」のように答えの形が最初から決まっているため、順番に組み立てる必要がありません。複数の質問への答えを同時に一発で出せるので、応答は 0.07〜0.5 秒程度、費用も文章を書くAIの数十分の一以下になります。

図3　上：文章を書くAIは1つずつ順に出力するので、長さに比例して時間がかかる。下：Jev は決まった形の答えを同時に出すので、質問が増えてもほとんど時間が延びない。

もっと詳しく：学習方法の違い（RLHF・RLVR・RLCD）

AIは「事前学習」で大量の文章を読んだあと、目的に合わせて追加の訓練を受けます。開発元はこの追加訓練を3系統に整理しています。

  • RLHF（人間のフィードバックによる強化学習）：人間が好む返事を出すよう訓練。ChatGPT を生んだ方法。
  • RLVR（検証可能な報酬による強化学習）：正解が機械的に確かめられる問題（数学など）で訓練。「推論モデル」を生んだが、遅くて高い。
  • RLCD（校正された判断のための強化学習）：Jev 独自の方法。文章を作らず、「判断」と「その判断がどれくらい当たるかの確率」を正しく出すよう訓練。

開発元は、RLHF には「人間に気に入られようとして迎合する」「自信満々に間違える」といった副作用があり、それが「AIに任せきれず人間が見張り続けなければならない」原因だと主張しています。

なお RLCD の中身（報酬の設計、学習手順など）は公開されておらず、論文も出ていません。この点は 7. 注意点 で扱います。

5.「信頼度」という便利な数字

要点Jev は答えごとに「どれくらい自信があるか」を数字で返す。自信が高ければ自動で進め、低ければ人に回す、という仕組みが作れる。

Jev の答えには、選択肢や点数だけでなく信頼度（confidence）という 0〜1 の数字が付いてきます（「はい/いいえ」型は確率そのものが答えなので、信頼度は付きません）。これが実務でとても重要です。

例え話：天気予報の「降水確率」

「降水確率 90%」なら傘を持って出かけ、「50%」なら迷って折りたたみ傘にし、「10%」なら持たない——人は確率に応じて行動を変えます。

Jev の信頼度も同じです。「自信 0.95 なら自動で処理、0.6 なら人が確認、0.3 なら人に任せる」とプログラムに書いておけば、AIに任せる範囲を安全に調整できます。

図4　信頼度に応じて「自動／確認／人に回す」を切り替える。操作の重さによって境界を変えるのがポイントで、取り消せない操作ほど自動化の範囲を狭くする。

公式ドキュメントが強調しているのは、境界（しきい値）は1つではないということです。「問い合わせの振り分け」と「取り消せない送金の承認」が同じ基準で自動化されてはいけません。「どこまでAIに任せるか」というリスク判断を、プログラムの中に数字として書き込む——これが Jev の想定する使い方です。

もっと詳しく：「校正（キャリブレーション）」とは

Jev の信頼度が役に立つのは、その数字が「校正」されている——つまり「0.8 と答えたケースを集めると実際に約80%が正解」という性質を目指して訓練されているからです。天気予報でいえば「降水確率70%と言った日の7割で実際に雨が降る」のが校正された予報です。

ただし公式ドキュメントも「個々の答えが正しいことの保証ではない」と明記しています。レビュアーの Anthony Maio 氏は「常に平均的な確率を答えるだけのAIでも校正はできてしまう。校正されていることと役に立つことは別」と指摘しています。

6.数字で見る実力（と読み方）

要点賢さは「中堅クラスのAIと同程度」。速さと安さは桁違い。ただし最上位のAIには少し劣り、数字はすべて開発元自身の計測。

開発元は、4種類の業務（セキュリティ対応・AIエージェントの動作チェック・請求書処理・カスタマーサポート）で、Jev と主要なAIを同じ条件で比べた結果を公開しています。「正解」は最上位クラスのAI2つ（GPT-6 Astra と Claude Fable 5.1）の答えの平均を使い、それとどれだけ一致するかを見ています。

もっと詳しく：デモ（Doom・Wikiracing）とエラー率の話

公式サイトのデモ：同じ判断を Jev は 0.114秒／$0.000081、中堅クラスのLLMは 8.566秒／$0.013880 で処理。ただし開発元自身が「このデモは意図的に単純化しており、自社に有利」と注記しています。

Doom：ゲームの状態（画像ではなくデータ）を毎秒10回 Jev に送って操作させるデモ。費用は約$7/時。開発元は「AIでない普通のボットのほうが上手いが、いろいろな状態表現に反応するボットを作りたかった」と正直に書いています。

Wikiracing：Wikipedia のリンクだけをたどって目的のページに着く遊び。1手ごとに数百〜数千のリンクから選ぶため、「存在しない選択肢を答えない」Jev の性質が活きます。ただし一度に選べる選択肢は最大255個で、それを超えると2段階処理になり遅くなります。

構造化出力のエラー率：Jev は仕組み上 0%。比較として他のAIでは 0.58%〜45.5% のエラー率が示されていますが、開発元自身が「他社の数値は測定条件が違い、バイアスがほぼ確実にある」「自社の0%は実測ではなく仕組み上の保証」と明記しています。単純比較はできません。

7.注意点とよくある誤解

要点「間違えないAI」ではない。形は崩れないが中身は間違える。理由を説明してくれないので、監査が必要な業務には工夫が要る。

  1. 誤解①「ハルシネーション（でたらめ）がない」＝「間違えない」ではない Jev が保証するのは答えの形だけです。「請求／技術／営業」から選べと言われて「経理」と答えることはありませんが、本当は請求なのに技術と答えることはあります。しかも、その間違った答えに高い信頼度を付けることもあります。レビュアーの言葉を借りると「Jev は答えの形を縛るが、判断そのものは縛らない」です。
  2. 選択肢の作り方を間違えると、静かに壊れる 正解が選択肢の中にないとき、Jev は用意された選択肢のどれかを必ず選びます。「その他」「分からない」「情報不足」という逃げ道を必ず入れておく必要があります（公式も推奨）。
  3. 「なぜそう判断したか」を教えてくれない 文章を書かないので、理由の説明がありません。「なぜこの申請がこの点数なのか」と聞かれる業務（審査・監査など）では、信頼度の数字だけでは説明になりません。対策は、大量処理は Jev、説明が必要なものは文章を書くAIか人に回すという組み合わせです。
  4. 世の中が変わると精度が落ちる ルール変更、新しい種類の顧客、新しい不正の手口などが出てくると、先月まで信頼できた確率が静かにずれていきます。定期的な見直しが必要です。
  5. まだ検証途中の技術 学習方法（RLCD）の中身は非公開で論文もなく、評価は開発元の自己採点です。価格が今後も維持されるかも「長期で示すしかない」と開発元自身が書いています。現時点では「有望だが、まだ様子見」が妥当な評価です。
もっと詳しく：その他の注意点
  • 個別に正しい確率でも、組み合わせると保証は消える。 複数の判断をしきい値や分岐で組み合わせたワークフロー全体が、自動的に「校正されている」わけではありません（似た原因の間違いは組み合わせても残る）。
  • しきい値はモデルのバージョンに依存する。 新バージョンが出ると同じ 0.8 でも意味が変わりうるため、しきい値を調整したら jev-1.13.0 のようにバージョンを固定し、自分のタイミングで移行することを公式も勧めています。
  • 画像は扱えない。 現時点では文字データのみ。Doom のデモもゲームの状態を文字データにして渡しています。
  • 「JSONモードと何が違うのか」は決着していない。 既存のAIにも「決まった形式で出力させる」機能はあります。開発元は「並列で速い・形式違反が不可能・確率が校正されている」の3点を違いとして挙げていますが、「既存技術で数週間あれば同等のものが作れる」という反論もあり、議論が続いています。
  • 使い道の両面性。 The Register は「これだけ速く安く判断できるなら、ドローンの照準判断に使えという要求が出るのも時間の問題」と皮肉を書いています。速く安い自動判断は、どこまで任せてよいかという倫理の問題も連れてきます。

8.私たちの仕事にどう関係するか

要点「AIに文章で丸投げしていた仕事」を見直し、「実は分類・判定だけ」の部分を切り分ける。この考え方は Jev を使わなくても効く。

Jev の登場で見えてくるのは、これからのAI活用は1つの賢いAIに何でも任せるのではなく、役割ごとに分担させる形になりそうだ、ということです。

図6　これからのAI活用の役割分担のイメージ。文章を書くAI・判断するAI・プログラム・人が、それぞれ得意なことを担う。

今日からできること

  1. AIに任せている仕事を棚卸しする（Jev がなくてもできる） 今 ChatGPT などに文章で頼んでいる作業のうち、「実は分類・振り分け・採点・はい/いいえの判定に過ぎないもの」を洗い出す。6. の評価が示したとおり、どのAIでも「小さな判断に分ける」だけで精度・速度・費用が改善します。
  2. 試すなら「失敗しても安い場所」から Jev は現在、順番待ちリスト経由の早期アクセスです。最初の実験は、AIの出力の品質チェックや問い合わせの一次振り分けなど、間違えてもすぐ直せる工程から。取り消せない操作（承認・送金など）の自動化から始めない。
  3. 評価は自社データで、全体の費用で 開発元の数字を鵜呑みにせず、自社のデータで精度を測る。費用は「AIの呼び出し1回いくら」ではなく、人の確認や別のAIへの回送も含めた業務全体で比較する。
  4. 問うべきは「どこまで任せられるか」 「安くて速い」は前提として、その業務で許容できる間違いの割合はどれくらいで、その範囲でどこまで自動化できるかを考える。説明責任が必要な業務には、最初から「人や文章を書くAIに回す経路」を設計に入れておく。

用語集

LLM（大規模言語モデル）
ChatGPT や Claude のように、大量の文章を学習して文章で答えるAIの総称。この資料では「文章を書くAI」と呼んでいます。
トークン
AIが文章を数えるときの単位。おおよそ「単語や文字のかたまり」。AIの料金は「トークン何個分」で計算されるのが一般的です。
ハルシネーション
AIがもっともらしい嘘や、存在しない情報を作り出してしまうこと。「幻覚」の意味。
構造化データ／型
「請求／技術／営業のどれか」「0〜1の数値」のように、取りうる値の形があらかじめ決まっているデータのこと。プログラムはこういうデータを扱うのが得意です。逆に自由な文章は「非構造データ」。
API
プログラムから別のサービスを呼び出すための窓口。Jev は API を通じてプログラムから使います。
確率と信頼度
確率は「各選択肢がどれくらいありそうか」の分布。信頼度はそれを「どれくらい自信があるか」の1つの数字（0〜1）にまとめたもの。
校正（キャリブレーション）
「80%と言ったときに実際に約80%当たる」のように、確率の数字と実際の的中率がそろっている状態。
しきい値
「信頼度 0.9 以上なら自動処理」のように、処理を切り替える境界の数字。
RLHF / RLCD
AIの追加訓練の方法の名前。RLHF は「人間の好みに合わせる」訓練で ChatGPT を生んだもの。RLCD は Jev 独自の「正しい確率で判断する」訓練。
早期アクセス
正式公開前に、申し込んだ一部の利用者だけが試せる段階。仕様や価格が変わる可能性があります。
System One Model
TypeSafe が名付けた Jev の分類名。心理学の「速くて直感的な思考（システム1）」と「遅くて熟考する思考（システム2）」の区別が元になっています。標準的な業界用語ではなく、開発元の呼び方です。
