SECTION 1概要（3行で）

SUMMARY
  • Dockerは、アプリケーションと実行環境をひとまとめにして「コンテナ」という軽量な箱に入れ、どこでも同じように動かせるようにするツール（プラットフォーム）である。
  • 「自分のPCでは動くのに本番環境では動かない」という問題を解消し、開発・テスト・本番の環境差をなくすために広く使われている。
  • 仮想マシンより軽量・高速に起動できる点が特徴で、現在はクラウド開発やマイクロサービス、CI/CDの基盤技術として定着している。

SECTION 2基本用語

用語意味
コンテナ（Container）アプリケーションとその実行に必要なライブラリ・設定をまとめて隔離した、実行中の軽量な環境。
イメージ（Image）コンテナを作るための「読み取り専用のひな形」。OSの一部やアプリ、ライブラリなどが層（レイヤー）状に重なって構成される。
Dockerfileイメージの作り方を記述したテキストファイル。「どのベースイメージを使い、何をインストールし、何を実行するか」を命令として並べる。
レジストリ（Registry）イメージを保存・配布する場所。公開レジストリの代表例が Docker Hub。
Docker Engineコンテナを実際に動かす本体。ユーザーが使う「クライアント（CLI）」と、裏で動く「デーモン（dockerd）」から成る。
Docker Compose複数のコンテナをまとめて定義・起動するためのツール。YAMLファイルで構成を書く。
ボリューム（Volume）コンテナを削除してもデータを残しておくための永続化の仕組み。

※ 表は横にスクロールできます。

SECTION 3仕組み・全体像

3-1. 全体の流れ

Dockerの基本的な流れは次のようになる。

  1. 開発者が Dockerfile を書く（「このOSをベースに、このライブラリを入れて、このコマンドで起動する」という手順書）。
  2. docker build コマンドで Dockerfile から イメージ を作成する。
  3. イメージを docker run で実行すると、コンテナ（実行中のインスタンス）が起動する。
  4. 作成したイメージは レジストリ（Docker Hubなど）に push して保存・共有でき、他の人や別のサーバーはそこから pull して同じ環境を再現できる。

3-2. アーキテクチャの主要コンポーネント

コンポーネント役割
Docker クライアントユーザーが docker run などのコマンドを打ち込むインターフェース。
Docker デーモン（dockerd）クライアントからの指示を受けて、実際にイメージのビルドやコンテナの起動・管理を行う本体プロセス。
レジストリイメージの保管・配布を行う。Docker Hubが代表例。

3-3. コンテナと仮想マシン（VM）の違い

両者とも「環境を隔離して動かす」技術だが、仮想化するレイヤーが異なる。

仮想マシンはハードウェアレベルから丸ごと仮想化し、それぞれが独立したOSを持つ。一方、コンテナはホストOSのカーネルを共有し、その上でアプリケーションだけを隔離して動かす。

観点仮想マシン（VM）コンテナ（Docker）
仮想化する範囲ハードウェアからOSまるごとOSのカーネルは共有し、アプリ層のみ
起動時間数分程度数秒程度
サイズ数GB〜数十〜数百MB程度
隔離の強さ強い（別OS・別カーネル）カーネルを共有するためVMよりやや弱い（namespaceやcgroupで隔離を実現）
密度1台のホストに置ける数が少ない同じホストでより多く同時実行できる

※ 表は横にスクロールできます。

SECTION 4具体例・使いどころ

4-1. 開発環境の統一

「自分のPCでは動くのに、他の人のPCやサーバーでは動かない」という問題を防ぐため、Dockerfileに環境構築手順をコード化しておき、チーム全員・本番環境で同じイメージを使う、という使い方が代表的。

4-2. マイクロサービス・複数コンテナの管理

Webサーバー、アプリケーションサーバー、データベースなど役割ごとにコンテナを分け、Docker Compose でまとめて起動・停止する構成がよく使われる。

各サービスを独立して開発・デプロイできるマイクロサービス的な設計と相性がよい。 

# docker-compose.yml のイメージ例（簡略化）
services:
  web:
    build: ./web
    ports:
      - "8080:80"
  db:
    image: postgres:16
    volumes:
      - db_data:/var/lib/postgresql/data
volumes:
  db_data:

4-3. CI/CDでの活用

テストのたびに毎回同じクリーンな環境をコンテナとして立ち上げ、終わったら破棄する、という使い方でCI/CDパイプラインの再現性を高められる。

4-4. Kubernetesなどオーケストレーション基盤との連携

本番で多数のコンテナを運用する場合は、Kubernetesのようなオーケストレーションツールと組み合わせて、コンテナの自動配置・スケーリング・自己修復などを行うのが一般的。

SECTION 5注意点・よくある誤解

CAUTION
  • 「コンテナ＝軽量な仮想マシン」ではない。 ホストOSのカーネルを共有する仕組みであり、独立したOSを持つVMとは隔離のレベルが異なる。用途に応じて使い分けが必要。
  • コンテナを削除するとデータも消える。 コンテナ内に保存したファイルはコンテナと一緒に消えるため、データベースなど残したいデータはボリュームを使って永続化する必要がある。
  • 「Docker」＝「Docker Desktopの起動」ではない。 Windows/Macでは裏でDocker Desktop（もしくはWSL2など）が動いている必要があり、これが起動していないだけの「動かない」トラブルが非常に多い。
  • ポート衝突・権限エラーに注意。 指定したポートが既に使われている、LinuxでDockerグループに属していないためpermission deniedになる、といった初心者がつまずきやすいエラーがある。
  • DockerだけがコンテナランタイムではないというWKの変化。 Kubernetesは v1.24 でDockerを直接のランタイムとして使うのをやめており、OCI（Open Container Initiative）標準に準拠したPodmanなど別のツールも普及しつつある。「コンテナ＝Docker」と決め打ちしない方がよい。

SECTION 6確認問題

Q1.Dockerの「イメージ」と「コンテナ」の違いを一言で説明してください。

答えを見る

イメージは実行環境の「読み取り専用のひな形（設計図）」であり、コンテナはそのイメージを実際に実行している「動いているインスタンス」である。

Q2.コンテナが仮想マシン（VM）より起動が速く、軽量な理由を説明してください。

答えを見る

VMはハードウェアからOSまで丸ごと仮想化し、各VMが独自のOSを持つのに対し、コンテナはホストOSのカーネルを共有し、アプリケーション層のみを隔離するため。ゲストOSの起動が不要な分、コンテナは数秒で立ち上がり、サイズも小さくて済む。

Q3.Dockerfile、イメージ、レジストリの関係を、処理の流れの順に説明してください。

答えを見る

Dockerfileに環境構築の手順を書き、それを docker build することでイメージが作られる。作成したイメージは docker run でコンテナとして実行できるほか、レジストリ（Docker Hubなど）に push しておくことで、他の環境から pull して同じイメージを再利用できる。

Q4.コンテナ内で作成したデータをコンテナ削除後も残したい場合、どうすればよいですか。

答えを見る

Dockerの「ボリューム（Volume）」を使ってデータを永続化する。ボリュームはコンテナのライフサイクルとは独立して存在するため、コンテナを削除してもデータは残る。

Q5.Docker Composeはどのような場面で使われますか。

答えを見る

Webサーバー、アプリケーションサーバー、データベースなど複数のコンテナを組み合わせて一つのシステムを構成する場合に、YAMLファイルで構成をまとめて記述し、1つのコマンドでまとめて起動・停止するために使われる。マイクロサービス開発や、開発環境の自動化、CI/CDでのテスト環境構築などによく利用される。
