すべてのタスクに専用ハーネスを

  • 対象プラン Pro / Max / Team / Enterprise

  • 状態 Research preview（Claude Code v2.1.154+、ベストプラクティスは発展途上）

概要

3行でいうと
  1. Dynamic workflowは、Claudeが書いたJavaScriptスクリプトがループ・分岐・中間結果を保持しながら最大数百のサブエージェントを動かす仕組みで、タスク専用のハーネスをその場で生成できる。
  2. 長時間・大規模・敵対的なタスクを1つのコンテキストで進めると起きる失敗モード（agentic laziness・self-preferential bias・goal drift）を、別々のコンテキストを持つClaudeに分割することで構造的に防げる。
  3. /deep-research <質問>やultracodeキーワード（「ワークフローを使って」でも可）ですぐ試せる。履歴書ランキングなど非技術タスクにも強いが、トークン消費が大きいので、まず小さな範囲で「10k tokens まで」のような予算指定から始める。

Dynamic workflowは、Claudeがその場でタスク専用のハーネス（harness）を書き、多数のサブエージェントをオーケストレーションする仕組みです。本ガイドは公式リファレンスに加え、実例プロンプト・設計パターン・ユースケース・運用Tipsをまとめています。

補足

本ガイドは公式リファレンスに加え、Anthropicの「A harness for every task」記事の実践的知見を統合したものです。ベストプラクティスは現在も発展途上です。

基本用語

Dynamic workflowとstatic workflow

以前からClaude Agent SDKやclaude -pで複数のClaude Codeを協調させるstatic workflowを作れました。違いは「事前に汎用的に書く」か「その場で専用に書かせる」かです。

補足

仕組み・全体像

なぜdynamic workflowsが必要か

デフォルトのハーネスは、計画と実行を同じコンテキストウィンドウで行います。多くのコーディングタスクでは有効ですが、長時間・大規模並列・高度に構造化された敵対的タスクでは破綻することがあります。

同一コンテキストで複雑なタスクに長く取り組むほど、Claudeは次の特定の失敗モードに陥りやすくなります。ワークフローは、それぞれ独立したコンテキストウィンドウと焦点を絞った隔離されたゴールを持つ複数のClaudeをオーケストレーションすることで、これらに対抗します。

長い作業ほど1つの文脈で抱えない
失敗モード説明ワークフローによる対策
Agentic laziness（怠惰） 複雑で多部構成のタスクで、部分的な進捗のまま完了を宣言してしまう。例: セキュリティレビューの50項目中20項目だけ対処して終わる。 各項目を独立エージェントに割り当て、スクリプトが完了をすべて待つ（barrier）。
Self-preferential bias（自己優先バイアス） 自分の結果や発見を、特にルーブリックで検証・採点させたときに優先しがち。 別の独立エージェントが敵対的に検証する（adversarial verification）。
Goal drift（目標のずれ） 多数のターン、特にcompaction（要約圧縮）後に、当初の目的への忠実度が徐々に失われる。「Xをするな」のような制約やエッジケース要件が欠落しやすい。 各エージェントに焦点を絞った固定ゴールを与え、スクリプトが原典の目標を保持する。

実行の仕組みと制限

ランタイムは会話と別の隔離環境でスクリプトを実行。中間結果はスクリプト変数に残ります。

各実行はスクリプトを~/.claude/projects/配下に書き出し、開始時にClaudeがパスを受け取ります。読んだり、過去実行とdiffしたり、編集して再起動を頼めます。ランタイムが各エージェントの結果を追跡するため、同一セッション内で再開可能です。

制約理由
実行中のユーザー入力なし停止できるのはエージェントの権限プロンプトのみ。段階承認が必要なら各段を別ワークフローに
ワークフロー自体からのFS／シェル直接アクセスなし読み書き・実行はエージェント。スクリプトは調整役
同時実行最大16エージェント（低コア機ではより少）ローカルリソース抑制
1実行あたり合計1,000エージェント暴走ループ防止

設計パターン6種

Claudeがワークフロー構築時に使い、組み合わせる代表的なパターンです。

プロンプトビルダーの仕組み

上のパターンを選び、タスクを入力すると、ワークフロー起動用プロンプトの叩き台を生成するツールです（例: 「src/routes/配下の全APIエンドポイントの認証チェック漏れを監査」）。「トークン予算を付ける（10k tokensまで）」のチェックも選べます。パターンごとの一言ガイドは次のとおりです。

  • Classify-and-act: 分類エージェントでタスク種別を判定し、種別ごとに別エージェントへルーティングする。
  • Fan-out-and-synthesize: タスクを小ステップに分割して各々を別エージェントで実行し、全完了を待ってから結果を統合する（fan-out-and-synthesize）。
  • Adversarial verification: 各生成結果を、別の検証エージェントがルーブリックに対して敵対的にレビューする。
  • Generate-and-filter: 多数の候補を生成し、ルーブリックと検証でフィルタ・重複除去して最良のものだけ残す。
  • Tournament: 複数エージェントに異なるアプローチで競わせ、判定エージェントがペアワイズ比較で勝者を決める。
  • Loop until done: 停止条件（新たな発見やエラーがなくなる）を満たすまでエージェントの起動を繰り返す。

選んだパターンとタスクから、次の形式でプロンプトが組み立てられます。

ultracode: {タスクの説明} — use a workflow.

次のパターンを使ってください:
・{選択したパターンの一言ガイド}

use 10k tokens.

技術・非技術を問わず、ワークフローが効く具体的な場面です。

領域やり方の要点主なパターン

メモリ／ルール遵守CLAUDE.mdに入れても守られないルールは、ルール1つにつき検証エージェント1体で点検。誤検知を減らすため懐疑役（skeptic）ペルソナでルールを精査。逆向きに、過去セッションやレビューコメントから繰り返す修正を抽出→クラスタリング→敵対的検証→CLAUDE.mdに蒸留も有効。fan-out / adversarial
根本原因調査独立した複数仮説を立てて検証するのがデバッグの定石。logs・files・dataなど互いに素な証拠から仮説を生成するエージェントを立て、各仮説を検証者・反証者のパネルにかける。コードに限らず、売上分析やデータパイプラインのpost-mortemにも。generate-and-filter / adversarial

探索とテイストデザインや命名などテイストに依る課題で、多数の案を探索しレビューエージェントにルーブリックを与える。基準を満たした時点で完了。トーナメントで順位付け・選定も。generate-and-filter / tournament
Evalsworktreeで別エージェントを起動し、比較エージェントがルーブリックに対して採点。作成したskillを特定基準で評価・改善する等の軽量evalに。tournament / adversarial
モデル／知能ルーティングタスクに合わせた分類エージェントが、事前リサーチで最適モデルを判定。例: 「authモジュールの仕組み説明」は対象ファイル数と構造に応じてSonnetかOpusにルーティング。classify

同梱ワークフローを実行する

最短で動きを確認するなら/deep-research。質問を多角的に調べ、ソースを相互検証して引用付きレポートを返します。

  1. ワークフローを実行する。調べたい質問とともに実行。複数角度にWeb検索をファンアウトし、ソースを取得・相互検証し、引用付きレポートを合成します。 
    /deep-research What changed in the Node.js permission model between v20 and v22?
  2. ワークフローを許可する。Claude Codeが可否を尋ねます。Yesを選択（プロンプトは権限モードによる、後述の「実行前にプランを承認する」を参照）。
  3. 進捗を見る。バックグラウンドで実行され、セッションは空いたまま。/workflowsで実行を選びEnterで進捗ビュー（フェーズごとのエージェント数・トークン・経過時間）。 
    /workflows
  4. レポートを読む。完了するとレポートが届きます。出典が引用され、相互検証を生き残らなかった主張は除外済みです。

プロンプトで依頼する

effortを変えずに単一タスクをワークフロー化するにはultracodeを含めます。「ワークフローを使って」など自然言語でも同じオプトインです。

ultracode: audit every API endpoint under src/routes/ for missing auth checks
バージョン差分

v2.1.160より前のリテラルトリガーはworkflow。自然言語の依頼は両バージョンで動作。誤起動はmacOS Option+W / Win・Linux Alt+Wで解除、または/configでトリガーをオフ。

ultracodeでClaudeに任せる

xhigh reasoning effortと自動オーケストレーションを組み合わせた設定。実質的な各タスクごとにClaudeがワークフローを計画します。

/effort ultracode
補足

現在のセッションのみ有効でリセットされます。通常作業は/effort highに戻します。xhigh対応モデルでのみ利用可。

実行前にプランを承認する

CLIのプロンプトは計画フェーズと選択肢（Yes, run it / Yes, and don't ask again… / View raw script / No）を表示。Ctrl+Gでエディタに開き、Tabでプロンプト調整。

サブエージェントは常にacceptEdits
権限モードプロンプトが出るタイミング
Default / accept edits毎回（「don't ask again」選択時を除く）
Auto初回のみ。以後は同意を記録し無確認。ultracode時はスキップ
Bypass / claude -p / Agent SDK尋ねず即開始
重要

生成されるサブエージェントは常にacceptEditsで動作し、ツール許可リストを継承。allowlist外のシェル・Webフェッチ・MCPは途中で確認することあり。長い実行では事前にallowlistへ追加を。

保存して再利用する

/workflowsで実行を選びs。Tabで保存先を切り替え（.claude/workflows/=プロジェクト共有/ ~/.claude/workflows/=自分専用）。Enterで保存し/<名前>として実行。同名はプロジェクト側が優先。

入力を渡す（args）。保存ワークフローはargsグローバルで入力を受け取れます。構造化データで渡されるため配列・オブジェクトメソッドを直接呼べます。省略時はundefined。

> Run /triage-issues on issues 1024, 1025, and 1030

構築のTips

プロンプティング。上記パターンの用語を使った詳細なプロンプトが最良の結果を生みます。ワークフローは大きなタスク専用ではなく、「quick workflow」も指定できます（例: ある前提の素早い敵対的レビュー）。

/goalと/loopを組み合わせる。トリアージ・リサーチ・検証など繰り返せるワークフローは、/loopで定期実行し、/goalで「これを満たすまで止まるな」という強い完了条件を設定すると効果的です。

トークン予算。「use 10k tokens」のように明示すると上限が設定され、暴走を抑えられます。

予算は「10k tokensまで」と明示する

保存と共有。ワークフローメニューでsを押して保存し、~/.claude/workflowsにチェックインするか、skillとして配布できます。skill経由で共有するには、JavaScriptファイルをskillフォルダに置きSKILL.mdから参照します。柔軟性のため、skill内のワークフローは「逐語実行するスクリプト」ではなくテンプレートとして扱うようClaudeに促すとよいでしょう。

注意点・よくある誤解

使わない方がよい時

よくある誤解

すべてのタスクに必要なわけではありません。ワークフローは大きな成果を生む場面が多い一方、不要なタスクでは大幅にトークンを浪費します。通常のコーディングタスクでは「本当に追加のcomputeが必要か？」を自問してください。多くの伝統的なコーディングタスクに、5人のレビュアーのパネルは要りません。

ワークフローは、これまでできなかった方向にClaude Codeを押し広げるために創造的に使うのが最良です。

実行の管理とコスト

一時停止後の再開。停止後も再開可能。完了済みはキャッシュ結果を返し、残りはライブ実行。/workflowsで選びp、または再起動をClaudeに依頼。同一セッション内のみで、Claude Code終了後の次セッションは最初からになります。

コスト。

  • まず小さく試す: 1ディレクトリ／狭い質問で。/workflowsが各エージェントのトークンを表示、完了分を失わず停止可。
  • 上限が歯止め: エージェント上限が暴走コストを抑制。
  • モデル確認: 大きな実行前に/model。不要なステージは小さいモデルをClaudeに指定。予算は「10k tokens まで」のように指定。

無効化。自分用は/configのトグル、~/.claude/settings.jsonの"disableWorkflows": true、またはCLAUDE_CODE_DISABLE_WORKFLOWS=1。組織用はmanaged settingsか管理設定ページのトグル。無効時は同梱コマンド不可、ultracode起動なし、/effortからultracodeが消えます。

確認問題

Q1. 自分のタスクにsubagents / skills / agent teams / workflowsのどれを使うべきか、どう判断すればよい？

次の3つの問いで判断します。

  • Q1. 必要なエージェントの規模は？ → 数件で足りる/数十〜数百体
  • Q2. このオーケストレーションを繰り返し再実行したい？ → 今回限り/毎回まわしたい（コード化したい）
  • Q3. 結果を相互検証・敵対的レビューで担保したい？ → 単一パスでよい/独立レビュー／多角的検討が欲しい

判定ロジックは次のとおりです。

  • 規模が「数十〜数百体」、または品質担保で「独立レビュー／多角的検討が欲しい」を選んだ場合: Workflows ── 多数のエージェントが必要、または相互検証・敵対的レビューで品質を担保したい場合は、スクリプトがプランを保持するワークフローが最適です。
  • 再利用が「毎回まわしたい（コード化したい）」の場合: Workflows（保存して再利用） ── オーケストレーションをコード化して繰り返したいなら、ワークフローを書いて/workflowsから保存しましょう。
  • 規模が「数件で足りる」の場合: Subagents / Skills ── 数件のタスクをターンごとに委譲するだけなら、Claudeがオーケストレーターとなるsubagentsやskillsで十分です。
